# Giver 아키텍처 전체 버전 성능 리포트

**핵심 지표**: 에이전트 1회 실행당 컨텍스트 크기.  
바이트(입력+출력 파일 크기) = 우리가 준 정보량. 토큰(LLM 실제 처리량) = 바이트 + 파일 읽기.  
과제가 복잡하면 턴이 많고 총 토큰도 커지는 건 당연하다. **1회 실행당 바이트와 토큰**을 함께 봐야 구조 효율성과 파일 읽기 과다를 모두 파악할 수 있다.

```
비율 = W_tokens 평균 / W_bytes 평균

v3.6.1:  171× (Worker가 프롬프트의 171배 토큰 처리 — 과다 읽기)
```

비율이 높을수록 Worker가 `read` 도구로 파일을 많이 읽었다는 뜻. v3.6.2는 v3.6.1 대비 **63% 감소**.

## 3. v3.6.1 vs v3.6.2: 토큰과 바이트 동시 비교 (18+5체인)

### 3.1 바이트 (프롬프트 크기)

| 메트릭 | v3.6.1 (18) | v3.6.2 (5) | 변화 |
|--------|:-----------:|:----------:|:----:|
| P_bytes 평균 | 8,112B | 5,649B | −30% |
| W_bytes 평균 | 4,920B | 2,201B | −55% |
| W_bytes 최대 | 11,527B | 5,707B | −50% |

### 3.2 토큰 (LLM 실제 처리량)

| 메트릭 | v3.6.1 (18) | v3.6.2 (5) | 변화 |
|--------|:-----------:|:----------:|:----:|
| P_tokens 평균 | 724K | 476K | −34% |
| W_tokens 평균 | 841K | 228K | **−73%** |
| W_tokens 최대 | 6.0M | 474K | **−92%** |

### 3.3 핵심 인사이트

**바이트 감소(55%) ≠ 토큰 감소(73%)**. 토큰 감소가 더 큰 이유:

- **v3.6.1**: Worker가 `read` 도구로 대형 파일을 많이 읽음 (tk/byte = 171×)
- **v3.6.2**: `[Read from:]` auto-inject로 불필요한 파일 읽기 감소 (tk/byte = 63×)
- **W_tokens 최대 6.0M → 474K (−92%)**: 과다 읽기 이상치가 사라짐

> fe9907dc의 P_tokens(124K)가 c2e86d3b(34K)보다 큰 건 Planner가 5개 task 파일을 작성해서. Worker 수(3→5) 증가가 P_tokens를 늘림.

> W_bytes평균(단일 Worker 부하)은 비슷: 3,559B vs 4,228B (+19%).

## 6. 진화 요약

```
버전          W_tokens평균  W_bytes평균  tk/byte   핵심 변화
────────────────────────────────────────────────────────────────────
v1           1.9M          —           —        fork 누수
v2           1.4M          —           —        fork 제거
v2.5b        103K          —           —        Do-When, DI
v3.5         113K          —           —        Planner 읽기 금지
v3.6.1       841K          4.9KB       171×     reads:false (과다 읽기)
v3.6.2       228K          3.6KB       63×      auto-inject (과다 읽기 −63%)
```

**v3.6.2 핵심 성과**:
- W_bytes 평균: 4.9KB → 3.6KB (−26%) — 프롬프트 경량화
- W_tokens 평균: 841K → 228K (−73%) — 과다 읽기 감소
- W_tokens 최대: 6.0M → 474K (−92%) — 이상치 해소
- tk/byte 비율: 171× → 63× (−63%) — 파일 읽기 효율 개선

## 9. 잔존 과제

1. **과다 읽기 원인**: v3.6.2에서도 tk/byte ≥ 100×인 체인 존재 (3e51c1a3: 117×). Worker가 여전히 과도한 파일 읽기를 함.
2. **대형 과제 검증**: v3.6.2가 5건. 더 복잡한 과제에서 tk/byte 비율 추적 필요.
3. **측정 단위 통일**: v1~v3.5는 토큰만, v3.6+는 토큰+바이트 둘 다 측정 가능.
4. **plan.md 부산물**: `output:"plan.md"` 내용은 사용되지 않으나 해로움도 없음.
