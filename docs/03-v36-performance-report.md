# Giver 아키텍처 성능 리포트 — 컨텍스트 크기 중심

**핵심 지표**: 에이전트 1회 실행당 처리한 컨텍스트 크기(입력 + 출력 바이트).  
과제가 복잡하면 턴이 많아지고 총 토큰도 커지는 건 당연하다. **1회 실행당 컨텍스트**가 구조적 효율성의 진짜 지표다.

---

## 1. 컨텍스트 크기란?

```
컨텍스트 = 입력 + 출력 = 에이전트가 1회 실행에서 처리한 총 정보량

P_ctx = Planner 입력 + Planner 출력
W_ctx = Worker 입력 + Worker 출력  (과제 복잡도와 구조 효율성의 합성)
```

과제가 크면 W_ctx도 커지지만, **동일 과제에서 구조가 좋으면 W_ctx가 작아진다.**
총 토큰은 과제 크기에 비롈 뿐 아니라 구조 비효율(과다 읽기, 중복 지시)에도 비례한다.
컨텍스트 크기는 구조 비효율을 직접 측정한다.

## 7. 잔존 과제

1. **대형 과제 검증**: v3.6.2가 4건(단순 과제 포함). 10K+ Task #0에서 W_ctx 추가 검증 필요.
2. **샘플 확대**: 4체인 → 10+ 체인에서 통계적 유의성 확보.
3. **W_ctx 이상치 원인**: v3.6.1에서 W_ctx > 8KB인 체인 4건. Planner 큐레이션 부족이 원인.
4. **plan.md 부산물**: `output:"plan.md"` 내용은 사용되지 않으나 해로움도 없음.

## 8. 결론

**컨텍스트 크기 = 과제 복잡도 × 구조 효율성**. 과제가 커지면 총 토큰도 커지지만, 구조 효율성은 버전 개선으로 꾸준히 개선된다.

v3.6.2의 핵심 성과:

- **W_ctx −52%**: Worker가 처리하는 정보량이 절반 이하로 감소
- **W_act_max −50%**: 활성 Worker 최대 컨텍스트 상한이 낮아짐
- **안정성 확보**: task 파일 경로 문제 근원 해결, 잔여 파일 간섭 불가
