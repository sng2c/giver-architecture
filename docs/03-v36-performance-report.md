# Giver 아키텍처 전체 버전 성능 리포트

**핵심 지표**: 에이전트 1회 실행당 컨텍스트 크기(입력 + 출력).  
과제가 복잡하면 턴이 많고 총 토큰도 커지는 건 당연하다. **1회 실행당 컨텍스트**가 구조 효율성의 진짜 지표다.

## 4. 동일 과제 비교: Redbis 10모듈 (44 테스트)

### 4.1 과제 개요

7개 소스 모듈 구현 + 1개 엔트리 포인트. 44개 테스트 전부 통과가 목표.
동일 과제를 여러 버전으로 수행한 결과를 비교한다.

### 4.2 과제별 ctx 비교

| 버전 | 체인 | 결과 | P_ctx | W수 | W_ctx합 | W_ctx평균 | W_ctx최대 | Total |
|------|------|------|-------|-----|---------|----------|----------|-------|
| **v3.5** | c2e86d3b | 44/44 ✅ | 6,579B | 3 | 10,677B | 3,559B | 4,073B | 17,256B |
| **v3.6.1** | c2e86d3b | 44/44 ✅ | 6,579B | 3 | 10,677B | 3,559B | 4,073B | 17,256B |
| **v3.6.2** | fe9907dc | 44/44 ✅ | 6,416B | 5 | 21,138B | 4,228B | 5,405B | 27,554B |

> c2e86d3b은 v3.5→v3.6.1 마이그레이션 직후 실행. 프론트엔드만 바뀌고 Worker 동작은 동일.

### 4.3 분석

**v3.6.2의 Total이 더 큰 이유**: Worker 5개(4 활성 + 1 no-op) vs v3.6.1의 3개.

| 지표 | v3.6.1 (3W) | v3.6.2 (5W) | 해석 |
|------|------------|------------|------|
| P_ctx | 6,579B | 6,416B | Planner 크기 거의 동일 |
| W수 | 3 | 5(4 활성) | v3.6.2가 더 세분화 |
| W_ctx평균 | 3,559B | 4,228B | 비슷 |
| W_ctx최대 | 4,073B | 5,405B | |
| W_ctx합(활성만) | 10,677B | 18,387B | Worker 수 차이 |
| W작업/파일 | 2.3개/W | 1.75개/W | v3.6.2가 더 세분화 |

**핵심**: 동일 과제에서 **W_ctx평균(단일 Worker 부하)은 비슷**. Total이 큰 건 Worker 수 차이에서 온다. 과제당 Worker 부하(W_ctx평균)가 구조 효율성의 지표다.

## 10. 잔존 과제

1. **측정 단위 통일**: v1~v3.5는 토큰, v3.6+는 바이트. 동일 과제에서 토큰/바이트 동시 측정 필요.
2. **대형 과제 검증**: v3.6.2가 5건. W_ctx_max가 10KB+인 과제에서 추가 검증 필요.
3. **W_ctx 이상치 원인**: v3.6.1에서 W_ctx > 8KB인 체인 4건. Planner 큐레이션 부족.
4. **plan.md 부산물**: `output:"plan.md"` 내용은 사용되지 않으나 해로움도 없음.
