# Giver 아키텍처에서 얻은 인사이트

**작성**: 2026-05  
**근거**: 모놀리식~v3.6.3, 28체인, 동일과제 실측, 9개 버전 진화

---

## 1. 문제의 원인이 보이는 곳에 없다

v3.6.1에서 Worker 토큰이 과다했을 때, 가설은 "Worker가 `read()`로 파일을 너무 많이 읽어서"였다. 이 가설은 반쯤 맞았다. v3.6.2에서 reads:auto-inject로 과다 읽기를 해소하니 tk/byte가 171× → 63×로 개선됐다. 하지만 여전히 63×였다.

v3.6.3에서 밝혀진 진짜 원인: Worker 토큰의 약 75%가 테스트 실행 출력이었다. 각 Worker가 `npx vitest run`(전체 44테스트)을 돌릴 때마다 수만 토큰의 테스트 출력이 컨텍스트에 쌓였다. `read()` 호출이 아니라 **실행 출력**이 과다 토큰의 주범이었다.

```
가시적 증상:   "Worker 토큰이 과다하다"
첫 가설:       "read() 과다" → v3.6.2 해소 → 여전히 63×
진짜 원인:     "검증 과다"  → v3.6.3 해소 → 12×
```

**교훈**: 가시적 증상과 실제 원인이 다를 수 있다. tk/byte 비율이 이걸 분리해냈다 — 바이트(우리가 넣은 정보)와 토큰(LLM이 처리한 양)의 갭이 "프롬프트 외부에서 무엇이 토큰을 만들었는가"를 보여줬다. 토큰만 보면 "많이 읽는구나"라고 착각하고, 바이트와 토큰을 같이 봐야 read()와 실행 출력을 분리할 수 있다.

측정 지표가 문제를 가린다. 토큰만 측정하면 과다 읽기와 과다 검증을 구분할 수 없다. 바이트+토큰+tk/byte 세 축이 있어야 원인을 직교 분해할 수 있다.

---

## 2. 직교(Orthogonal) 개선이 곱해진다

과다 읽기와 과다 검증은 완전히 독립적인 원인이다.

- **과다 읽기**: `read()` 도구로 대형 파일 반복 호출 → 프롬프트 외부에서 파일 내용이 컨텍스트에 유입
- **과다 검증**: `npx vitest run` 전체 스위트 실행 → 테스트 출력이 컨텍스트에 유입

하나를 고쳐도 다른 게 안 고쳐진다. 그래서 개선이 곱연산으로 누적된다:

```
v3.6.1 → v3.6.2: 과다 읽기 해소    → tk/byte 171× × 0.37 = 63×
v3.6.2 → v3.6.3: 과다 검증 해소    → tk/byte  63× × 0.19 = 12×
누적 효과:                              171× × 0.37 × 0.19 = 12×
```

두 독립 원인을 각각 고치니 효과가 0.07×까지 떨어진다. 하나의 원인으로 묶으면 분해 불가능하고, 직교 축으로 분해하면 각 축의 개선이 서로 간섭하지 않고 누적된다.

**교훈**: "토큰이 많다"를 하나의 원인으로 다루면 직교 분해를 놓친다. 증상은 하나지만 원인은 여러 축일 수 있다. 각 축을 독립적으로 식별하고 수정하면 개선이 곱해진다.

## 3. 턴 증가는 예측 불가하다 — 그래서 애초에 격리한다

구현이 어려우면 턴이 많아진다. 이건 예측 불가능하다. W4가 18턴/20 tools로 수정 루프를 돌 것을 사전에 알 수 없다.

모놀리식에서 턴이 증가하면 I/O가 누적되고, 스티어링(목표, 제약)이 컨텍스트 최하단으로 밀려난다. 턴이 진행될수록 코딩 I/O(소스, 테스트 출력, 에러 로그)가 스티어링을 잠식한다.

```
모놀리식 (턴 누적):
  턴 1:  스티어링 상단, I/O 작음
  턴 5:  스티어링 중간, I/O 증가
  턴 18: 스티어링 하단, I/O 지배 → 방향 상실 → 턴 더 증가 → 악순환

Giver Worker (fresh):
  턴 1: 스티어링 상단, I/O 0
  턴 6: 스티어링 상단 유지, 이 Worker의 I/O만 누적
  종료: 이 Worker의 I/O만, 다른 Worker I/O는 격리됨
```

핵심: **터진 증가 자체를 막을 수 없다.** 구현 난이도는 사전에 알 수 없다. 하지만 턴 증가의 **後果**를 통제할 수 있다. 격리는 각 Worker의 턴 누적을 다른 Worker로부터 분리한다.

```
모놀리식: 턴 N의 I/O가 턴 1의 스티어링을 잠식 → 수정 루프 진입 시 복구 불가
Giver:    턴 N의 I/O가 이 Worker 내에만 누적 → 다른 Worker의 스티어링은 보존됨
```

격리는 턴 증가를 예측하는 게 아니라, 턴 증가가 **전파되지 않도록** 한다. W4가 18턴을 돌아도 W1~W3의 결과는 보존되고, W5는 W4의 I/O 없이 fresh 시작한다.

실패 경로에서도 같다:
```
모놀리식 전체 실패: 115K 낭비 + 처음부터 재시작 (스티어링 다시 퇴화)
v3.6.3   W4만 실패: W1~W3 결과 보존 + W4만 재실행 (격리 유지)
```

**교훈**: 턴 증가는 예측 불가하므로, 애초에 격리해서 전파를 차단한다. 이게 "최소 침투"와 "관심사 격리" 원칙의 실체다 — 각 Worker의 턴 증가가 다른 Worker에 영향을 주지 않도록 벽을 세우는 것. 재시도 비용 O(1)은 이 벽의 결과물이지, 벽 자체의 목적이 아니다.

## 4. 컨텍스트는 자원(Resource)이다, 제약(Constraint)만이 아니다

모두가 "컨텍스트 윈도우 한계"를 이야기하지만, 이 프로젝트가 보여준 건 컨텍스트가 **할당해야 하는 자원**이라는 것이다.

세 가지 컨텍스트 모드가 각각 다른 자원 할당 전략이다:

| 모드 | 할당량 | 효과 |
|------|--------|------|
| Fresh | 최소 (T₀만) | 격리. 부모 노이즈 0. 하지만 정보도 0에서 시작 |
| Fork | 최대 (부모 전체) | 축적. 하지만 v1에서 Worker 평균 1.9M토큰 — 노이즈가 스티어링을 압도 |
| T₀ 압축 | 선택적 (7섹션) | 대화 전체를 ~5KB로 손실 압축. 정확도는 Giver의 압축 품질에 의존 |

Giver는 본질적으로 컨텍스트 할당 시스템이다. 각 경계에서 "이 에이전트에게 지금 필요한 정보가 무엇인가?"를 결정하고, 그것만 전달하며 나머지를 격리한다:

```
G→P:  격리율 99%  (Giver 대화 ~500K토큰 중 T₀ ~5KB만 전달)
P→Wₖ: 격리율 83~93%  (다른 Worker 태스크 격리)
Wₖ→G: 격리율 98~99%  (Worker 실행 전체 중 RESULT만 회수)
```

**교훈**: "컨텍스트가 부족하다"가 아니라 "컨텍스트가 너무 많이 들어온다"가 진짜 문제다. 각 에이전트에게 정확히 필요한 만큼만 컨텍스트를 할당하는 것이 핵심 설계 결정이다. GGON 원칙 3(인지 부하 관리)의 수학적 실체다 — 컨텍스트 할당의 최적화.

인사이트 #3과 연결: 턴 증가는 예측 불가하므로 격리로 전파를 차단한다(인사이트 #3). 컨텍스트 할당은 "어떤 스티어링을 보존할 것인가"의 설계 결정이다(인사이트 #4). T₀의 7섹션이 보존할 스티어링의 목록이고, 격리가 보존하지 않을 것(I/O 노이즈)의 차단 메커니즘이다.

## 5. T₀의 품질이 병목이다

v1~v3.5의 W/P 분석에서 명확한 패턴이 나타난다:

```
P_input < 100K → W/P > 10× (71%의 체인)
P_input > 1M  → W/P < 2×  (0%의 체인)
```

T₀가 부실하면 Worker가 직접 파일을 읽으러 간다. T₀가 충실하면 Worker가 T₀만으로 작동한다.

Giver의 T₀는 대화 전체(수십만 토큰)를 7섹션 ~5KB로 손실 압축하는 함수다. 이 압축의 품질이 하류 전체를 결정한다. Planner도 Worker도 T₀ 이외의 정보에 접근하지 않는 한 T₀의 정확도에 완전히 의존한다.

하류 최적화(reads:auto-inject, Target Verification)는 T₀의 불완전성으로 인한 2차 문제를 해결하는 것이다. Worker가 과다 읽는 건 T₀에 구현 패턴이 없어서. Worker가 전체 테스트를 돌리는 건 T₀에 검증 범위가 없어서.

**교훈**: 파이프라인 아키텍처에서 **가장 중요한 단일 설계 결정은 Giver가 T₀에 무엇을 포함하고 무엇을 제외하는가**다. 7섹션 구조가 이 결정의 체계적 프레임워크이고, 각 섹션의 누락이 하류에서 구체적 과다로 나타난다.

## 6. 설계 원칙은 발견된 것이지 발명된 게 아니다

GGON 5원칙은 처음부터 있던 게 아니다. 각 원칙은 구체적 실패의 일반화다:

| 원칙 | 발견된 실패 | 증거 체인 |
|------|------------|----------|
| 최소 침투 | Worker가 Target Files 밖 파일 수정 | v3.5 이전 체인에서 빈번 |
| 중앙 제어 존중 | Worker가 아키텍처 결정 자의적 내림 | "follow existing patterns" → Worker 81턴 루프 |
| 인지 부하 관리 | T₀가 너무 장황하거나 너무 빈약 | P_input < 100K → W/P > 10× |
| 관심사 격리 | Worker가 참조 파일까지 수정 | v3.5 초기 Signatures 불명확 |
| 리팩터 가치 | 보이스카우트 규칙으로 무분별 리팩터링 | Worker가 "개선"하며 범위 이탈 |

좋은 원칙은 "이런 실패가 반복된다"는 관찰에서 나온다. "이래야 한다"는 이념에서 나온 게 아니다.

**교훈**: 설계 원칙은 사후적(posteriori)이다. 반복되는 실패 패턴을 일반화한 것이 원칙이지, 원칙을 먼저 세워서 실패를 막은 게 아니다. "원칙부터 정하고 설계하는" 접근은 근사치일 뿐이고, "실패에서 원칙을 추출하는" 접근이 실제로 작동하는 원칙을 만든다. Giver의 9개 버전 진화가 이것의 증거다.

## 7. 메트릭 진화가 인사이트를 만든다

이 프로젝트의 메트릭은 진화했고, 각 진화가 새 인사이트를 만들었다:

| 메트릭 | 질문 | 드러낸 것 | 가린 것 |
|--------|------|----------|---------|
| 성공/실패 | "됐나?" | 작동 여부 | 왜 안 되는지, 왜 비싼지 |
| W/P 비율 | "Planner 큐레이션이 충분한가?" | Planner 부실 → Worker 과다 | 토큰의 원인 분해 불가 |
| bytes vs tokens | "프롬프트 외부에서 무엇을 했나?" | 읽기 vs 실행 분리 | Worker 간 비교 불가 |
| tk/byte | "Worker가 과도하게 처리했나?" | 과다 읽기/과다 검증 식별 | 동일과제 비교 불가 |
| 동일과제 비교 | "구조가 효율 vs 효과에 미치는 영향?" | 총토큰 ≠ 실제비용 | — |

각 메트릭은 이전 메트릭이 가리던 문제를 드러냈다. W/P 비율은 "Planner가 충분한가?"를 보여줬지만 Worker 토큰의 원인을 분해하지 못했다. tk/byte는 원인 분해를 가능하게 했지만 다른 과제와의 비교 기준이 없었다. 동일과제 A/B 비교는 구조적 가치(격리 vs 총토큰)를 정량화했다.

**교훈**: 새 인사이트는 새 메트릭에서 온다. 같은 메트릭으로 계속 보면 같은 결론에 머문다. 메트릭 자체를 진화시키는 것이 분석 능력을 확장하는 핵심이다. "무엇을 측정할 것인가"가 "무엇을 개선할 것인가"보다 먼저다.

## 8. 소설 은유가 아키텍처를 예측했다

로이스 로리의 《기억 전달자》 메타포는 처음에 직관적 유사성이었다. 하지만 분석이 진행될수록 이 유사성이 구조적으로 정확하다는 게 밝혀졌다:

| 소설 | 아키텍처 | 정확도 |
|------|----------|--------|
| 기억 전달자가 모든 기억 보유 | Giver가 모든 대화 컨텍스트 보유 | 정확 — Giver는 유일하게 전체 맥락을 가짐 |
| 수령자는 전달받은 것만 받음 | Worker는 T₀/태스크만 수신 | 정확 — Worker는 fresh, 컨텍스트 0에서 시작 |
| 고통의 전달 (giving of pain) | Past failures 섹션 | 정확 — 실패 기억을 선택적으로 주입 |
| 전달은 선택적이고 의도적 | T₀의 7섹션 구조 | 정확 — 포함/제외가 명시적 설계 결정 |
| 기억이 아래로 새지 않음 | 격리율 99% | 정확 — 하류로 컨텍스트 역류 차단 |

가장 중요한 구조적 통찰: **기억을 보유하는 에이전트와 작업을 실행하는 에이전트가 분리되어야 한다.** 소설에서 기억 전달자와 공동체가 분리된 이유와 같다 — 축적된 기억(컨텍스트)이 실행(작업)에 간섭하면 방향을 잃는다.

**교훈**: 좋은 은유는 구조적 예측력이 있다. "이건 ~같다"가 아니라 "이건 ~의 구조를 가졌다"일 때, 은유의 원천에서 검증된 해결 패턴을 가져올 수 있다. 기억 전달자의 "선택적 전달"이 T₀의 7섹션 압축 함수가 되었고, "고통의 전달"이 Past failures 섹션이 되었다.

## 요약

Giver 프로젝트가 주는 가장 큰 인사이트 하나로 말하면:

**턴 증가는 예측 불가하므로, 애초에 격리로 전파를 차단한다.** 각 Worker의 턴 증가가 다른 Worker에 영향을 주지 않도록 벽을 세우는 것 — 이게 최소 침투와 관심사 격리의 실체다. 재시도 O(1)과 스티어링 보존은 이 벽의 결과물이다.

이 격리를 구현하기 위해 필요한 것:
1. **컨텍스트를 자원으로 인식** — 넣는 것만큼 빼는 것도 설계 결정이다
2. **T₀ 압축 품질** — 파이프라인의 병목은 Giver의 압축 함수다
3. **직교 원인 분해** — 과다의 원인을 독립 축으로 나누면 개선이 곱해진다
4. **메트릭 진화** — 새 질문이 새 메트릭을 만들고, 새 메트릭이 새 인사이트를 만든다
5. **원칙은 사후적** — 실패에서 추출한 원칙만이 작동한다
