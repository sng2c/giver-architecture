# Giver 아키텍처 성능 분석 리포트

**최종 갱신**: 2026-05  
**측정**: 모놀리식 ~ v3.6.7, 바이트+토큰+tk/byte  
**과제**: redbis-coding-test (10모듈, 44 테스트) 동일 과제 실측 포함

---

## 1. 요약

Giver v3.6.7는 W₁의 불필요한 Planner 출력 수신을 제거하여 토큰 낭비를 줄인다. v3.6.6 체인(66ecddfd)에서 W₁이 74,357토큰의 Planner 출력을 수신했지만 실제로는 task1.md만 참조했다. v3.6.6은 검증 관련 회귀를 구조적으로 방지한다. v3.6.3은 Planner가 Target Verification을 제대로 분배하면 12×, 전체 스위트를 복사하면 49×로 Planner 컴플라이언스에 따라 4배 차이가 났다. v3.6.6는 T₀에서 Target Verification 섹션을 제거하여 Planner가 검증 명령을 복사하는 것 자체가 불가능해졌다.

v3.6.2의 과다 읽기, v3.6.3의 과다 검증을 연속 해소하여, 총 W_tokens는 v3.6.1 대비 **97% 감소**했다.

```
v3.6.1 → v3.6.2 → v3.6.3 연속 개선
──────────────────────────────────────────────────────
W_tokens 평균   841K → 228K → 56K
tk/byte          171× → 63× → 12×  (모놀리식 21×보다 낮음)
```

## 4. tk/byte 분석 (과다 처리 지표)

### 4.1 정의

```
tk/byte = Worker가 처리한 총 토큰 / 프롬프트 바이트 크기
```

| 범위 | 의미 |
|------|------|
| 1~5× | 이상적. 프롬프트 + 최소 검증만 |
| 5~20× | 정상. 코딩 + 관련 검증 |
| 20~50× | 과다. 불필요한 파일 읽기 또는 전체 테스트 스위트 |
| 50×+ | 심각. 대형 파일 반복 읽기 또는 수정 루프 |

### 4.2 과다 토큰 원인 분해

v3.6.2 Worker 토큰의 약 75%가 **테스트 실행 출력**이었다. `read()` 호출이 아니라 `npx vitest run` (전체 44테스트)의 출력이 Worker 컨텍스트를 지배했다.

```
v3.6.2 Worker 토큰 구성 (추정):
  코딩(파일 읽기/쓰기):     ~25%
  테스트 실행 출력:         ~75%  ← 전체 44테스트를 각 Worker가 반복 실행

v3.6.3 Worker 토큰 구성 (추정):
  코딩(파일 읽기/쓰기):     ~60%
  검증 실행 출력:           ~40%  ← 각 Worker가 Target Verification만 실행
```

이것이 v3.6.3의 핵심 기여: Worker가 **자기 검증만** 실행하여 과다 처리를 제거.

> **v3.6.3‡ (f7ef943b)**: Planner가 모든 Worker에 `npx vitest run`(1338테스트 전체 스위트)를 지정. Target Verification 의도(최소 검증)가 무력화됨. tk/byte 49× = v3.6.3†(12×)의 4배.  
> **v3.6.6**: T₀에서 Target Verification 섹션을 제거. Planner가 검증 명령을 복사하는 것이 구조적으로 불가능. Worker는 "각자 자기 범위만" 합리적 설명으로 직접 판단.

> **v3.6.3 개선**: 12× (Target Verification 효과). W3은 5×까지 도달.

### 4.4 v3.6.1→v3.6.2→v3.6.3 개선 경로

```
v3.6.1의 두 가지 과다 원인:
  1) 과다 읽기: Worker가 read()로 대형 파일 반복 읽기 → tk/byte 171×
  2) 과다 검증: Worker가 전체 테스트 스위트 반복 실행 → 토큰의 ~75%

v3.6.2: 과다 읽기 해소 (auto-inject)     → tk/byte 63× (과다 읽기 −63%)
v3.6.3: 과다 검증 해소 (Target Verif.)   → tk/byte 12× (과다 검증 −75%, Planner 순응 시)
v3.6.6: 구조적 방지 (T₀ 검증 섹션 제거) → Planner 복사 회귀 불가능
```

각 버전이 하나의 과다 원인을 해소. 직교적 개선.

## 5. W/P 비율 분석 (Planner 큐레이션 품질)

Worker 최대 input / Planner input 비율(W/P). W/P가 낮을수록 Planner 큐레이션이 충분하여 Worker가 파일을 적게 읽는다. v3.6+에서는 tk/byte가 더 직접적 지표지만, W/P는 여전히 Planner 역할을 평가하는 데 유용하다.

### 5.1 W/P 분포 (18체인, v1~v3.6.1)

| 등급 | W/P 범위 | 체인 수 | 비율 | 의미 |
|------|---------|:------:|:----:|------|
| 🟢 효율 | < 5× | 8 | 44% | Planner 큐레이션 충분 |
| 🟡 양호 | 5~15× | 4 | 22% | 일부 Worker 과다 |
| 🔴 비효율 | 15~50× | 2 | 11% | Worker가 Planner 15~50배 더 읽음 |
| 💀 치명 | > 50× | 2 | 11% | Worker 50× 이상 더 읽음 |

### 5.2 P_input < 100K = W/P 악화

Planner 입력이 100K 미만이면 T₀가 불충분하여 Worker가 직접 파일을 읽는다.

| P_input 범위 | 체인 수 | W/P > 10× 비율 |
|-------------|:------:|:-----------:|
| < 100K | 7 | **71%** (5/7) |
| 100K~1M | 5 | 20% (1/5) |
| > 1M | 6 | 0% (0/6) |

### 5.3 v3.6+ 변화

v3.6.2에서 Planner 입력이 T₀ 한 개 파일로 제한되면서 P_input이 줄었다. 하지만 Worker의 reads:auto-inject가 과다 읽기를 막아 W/P는 의미가 변했다. v3.6.3에서는 tk/byte가 더 정확한 지표.

## 6. 모놀리식 vs Giver: 구조적 가치

### 6.1 토큰 대 격리

| 지표 | 모놀리식 | v3.6.3 | 해석 |
|------|---------|--------|------|
| 총 토큰 | **115K** | 421K | 모놀리식이 3.7× 적음 |
| Worker당 평균 | 115K | **56K** | **v3.6.3이 절반** |
| tk/byte | 21× | **12×** | **v3.6.3이 더 효율적** |
| 부분 재시도 | 불가 | **Worker 단위** | Giver만 제공 |
| 컨텍스트 격리 | 없음(누적) | **fresh** | Giver만 제공 |
| 병렬 실행 | 불가 | **가능** | Giver만 제공 |

### 6.2 재시도 비용 비교

모놀리식의 총 토큰이 적은 건 **1번만 검증**하기 때문이다. 하지만 한 번 실패하면 전체 재시작해야 한다.

```
모놀리식 성공:     115K
모놀리식 W1실패:  115K + 115K = 230K (처음부터 재시작)

v3.6.3 전체 성공:  421K
v3.6.3 W4만 실패: 304K + 117K = 421K (W4만 재실행, 다른 결과 보존)
```

Giver의 가치는 **총 토큰 최소화가 아니라 격리와 재시도**다. 실패 확률이 0이 아니면 Giver가 유리하다.

### 6.3 격리율

| 경계 | 전달 (스티어링) | 격리 (코딩 I/O) | 격리율 |
|------|--------------|---------------|--------|
| G → P | T₀ | Giver 대화 (~500K토큰) | **99%** |
| P → Wₖ | taskₖ.md | 다른 Worker 태스크 | **83~93%** |
| Wₖ → G | RESULT | Worker 실행 전체 | **98~99%** |

> 격리율 = 1 − (전달 크기 / 격리 전 컨텍스트 크기). 출처: c2e86d3b 체인 측정

## 10. W4 이상치 분석 (v3.6.3, 27×/117K)

v3.6.3 W4는 다른 Worker(5~12×)보다 tk/byte가 높다 (27×, 117K토큰, 18턴/20 tools).

**원인**: 검증 범위가 아니라 **구현 복잡도**. server/index.ts 구현이 복잡하여 테스트 실패 → 수정 → 재실행 루프가 18턴 발생. Target Verification에 지정된 `server.test.ts + tsc --noEmit`은 범위가 적절했지만, 루프 자체가 토큰을 만든다.

**개선 방향**: Planner가 복잡한 태스크를 더 세분화하면(예: server 생성과 connection 처리 분리) 수정 루프가 짧아질 수 있다.

## 9. 잔존 과제

1. **v3.6.3 Planner 컴플라이언스**: f7ef943b에서 Planner가 Target Verification 의도를 무시하고 전체 스위트 지정. Planner 프롬프트 강화 또는 T₀ 구조적 제약 필요.
2. **v3.6.3 샘플 확대**: 대규모 과제(1338테스트)에서 v3.6.3†=12×, v3.6.3‡=49×. Planner 컴플라이언스가 핵심 변수.
2. **태스크 분할 최적화**: W4(27×)와 W3(5×)의 차이에서, Planner의 분할 전략이 tk/byte에 미치는 영향 분석.
3. **측정 단위 통일**: v1~v3.5는 토큰만, v3.6+는 토큰+바이트 측정 가능.
4. **Breaking forward 검증**: 모든 테스트 체인에서 Breaking="None"이었음. 실제 Breaking 항목 전달 검증 필요.
