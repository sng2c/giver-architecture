# Giver 아키텍처 성능 분석 리포트

**최종 갱신**: 2026-05  
**측정**: 모놀리식 ~ v3.7.1, 토큰+바이트+in/turn  
**과제**: redbis-coding-test (10모듈, 44 테스트) 동일 과제 실측 포함

---

## 1. 요약

Giver v3.7.1은 results.md를 통한 구조적 Worker 간 통신을 도입하여 echo/forward 지시 의존성을 제거했다. v3.6.7~v3.6.8에서 echo/reproduce 지시가 모델에 의해 무시되는 것을 실측으로 확인하고, results.md reads 자동 주입으로 교체했다.

v3.6.2의 과다 읽기, v3.6.3의 과다 검증을 연속 해소하여 W_tokens는 v3.6.1 대비 **97% 감소**했다.

```
v3.6.1 → v3.6.2 → v3.6.3 연속 개선
──────────────────────────────────────────────────────
W_tokens 평균   841K → 228K → 56K
in/turn          93K → 63K → 12K
```

## 2. in/turn 분석 (Worker 처리 효율)

### 2.1 정의

```
in/turn = Worker 입력 토큰 / Worker 턴 수
```

모델이 읽은 컨텍스트 크기. 출력 토큰은 모델이 생성한 것이므로 컨텍스트 효율성의 척도가 아니다. 입력 토큰만이 "처리 비용"이다.

| 범위 | 의미 |
|------|------|
| 5~15K | 효율적. 프롬프트 + 최소 검증 + 코딩 |
| 15~30K | 정상. 코딩 + 관련 검증 |
| 30~50K | 과다. 대형 파일 읽기 또는 전체 테스트 스위트 |
| 50K+ | 심각. 반복 읽기, 수정 루프, 전체 스위트 반복 |

> (input+output)/turn과 수치 차이는 1~4%이지만, in/turn이 "모델이 처리한 컨텍스트"를 정확히 측정한다.


(in/turn = input 토큰/turn. (input+output)/turn과 수치 차이 1~4%)

과제별 특성(t스위트 수, 파일 크기)이 in/turn에 큰 영향. v3.7.0/3.7.1의 19K는 v3.6.7(12K)보다 높지만, 과제가 다름(Redis 1338테스트 vs 44테스트).

## 4. 과다 처리 원인 분해

### 4.1 직교 원인: 과다 읽기 × 과다 검증

v3.6.2의 과다 읽기와 v3.6.3의 과다 검증은 독립 원인. 개선이 곱해진다:

```
v3.6.1 → v3.6.2: 과다 읽기 해소    → in/turn 93K → 63K (−32%)
v3.6.2 → v3.6.3: 과다 검증 해소    → in/turn 63K → 12K (−81%)
누적 효과:                              93K → 12K (−87%)
```

### 4.2 과다 토큰 원인 분해

v3.6.2 Worker 토큰의 약 75%가 **테스트 실행 출력**이었다. `read()` 호출이 아니라 `npx vitest run` (전체 44테스트)의 출력이 Worker 컨텍스트를 지배했다.

```
v3.6.2 Worker 토큰 구성 (추정):
  코딩(파일 읽기/쓰기):     ~25%
  테스트 실행 출력:         ~75%  ← 전체 44테스트를 각 Worker가 반복 실행

v3.6.3 Worker 토큰 구성 (추정):
  코딩(파일 읽기/쓰기):     ~60%
  검증 실행 출력:           ~40%  ← 각 Worker가 Target Verification만 실행
```

이것이 v3.6.3의 핵심 기여: Worker가 **자기 검증만** 실행하여 과다 처리를 제거.

### 4.3 v3.6+ 과다 처리 원인 전환

| 버전 | 주요 원인 | in/turn | 해결 |
|------|----------|:-------:|------|
| v3.6.1 | 과다 읽기 | 93K | reads:auto-inject (v3.6.2) |
| v3.6.2 | 과다 검증 | 63K | Target Verification (v3.6.3) |
| v3.6.3† | Planner 과다 검증 | 12K | T₀ 검증 섹션 제거 (v3.6.6) |
| v3.6.3‡ | Planner 전체 스위트 복사 | 49K | T₀ 검증 섹션 제거 (v3.6.6) |
| v3.6.6 | W₁ Planner 출력 수신 | 36K | W₁ {previous} 제거 (v3.6.7) |
| v3.6.7 | {previous} 3회 치환 | 27K | 1회 치환 수정 (v3.6.7) |
| v3.6.8 | brief/echo 충돌 | 17K | "Write your RESULT" (v3.7.0) |
| v3.7.0 | W2 echo 미준수 | 19K | 결과 파일로 교체 (v3.7.1) |
| v3.7.1 | — | 19K | 구조적 통신 (results.md) |

> v3.6.6은 구조적 방지: T₀에서 Target Verification 섹션을 제거하여 Planner가 검증 명령을 복사하는 것 자체가 불가능. v3.7.1은 구조적 통신: echo 지시를 results.md reads 자동 주입으로 교체.

## 6. 모놀리식 vs Giver: 구조적 가치

### 6.1 토큰 대 격리

| 지표 | 모놀리식 | v3.6.3 | 해석 |
|------|---------|--------|------|
| 총 토큰 | **115K** | 421K | 모놀리식이 3.7× 적음 |
| Worker당 평균 | 115K | **56K** | **v3.6.3이 절반** |
| in/turn | 8K | **12K** | v3.6.3이 더 높음 (Task Verification 포함) |
| 부분 재시도 | 불가 | **Worker 단위** | Giver만 제공 |
| 컨텍스트 격리 | 없음(누적) | **fresh** | Giver만 제공 |

### 6.2 재시도 비용

모놀리식의 총 토큰이 적은 건 **1번만 검증**하기 때문이다. 하지만 한 번 실패하면 전체 재시작해야 한다.

```
모놀리식 성공:     115K
모놀리식 W1실패:  115K + 115K = 230K (처음부터 재시작)

v3.6.3 전체 성공:  421K
v3.6.3 W4만 실패: 304K + 117K = 421K (W4만 재실행, 다른 결과 보존)
```

## 10. 잔여 과제

1. **과제 특성과 in/turn**: v3.6.7(12K)와 v3.7.1(19K)의 차이는 절대적 효율이 아니라 과제 난이도 차이. 동일 과제 비교가 더 의미 있음.
2. **W4 이상치**: v3.6.3 W4(27K)가 다른 Worker(5~12K)보다 높음. 구현 복잡도로 인한 수정 루프. Planner가 복잡한 태스크를 더 세분화하면 개선 가능.
3. **Planner 과다 읽기**: 66ecddfd(12K)가 최저 in/turn이지만 Planner가 30턴 소요. Planner 읽기 최적화 필요.
4. **results.md 신뢰성**: Worker가 results.md에 append하는 것은 파일 쓰기 지시이므로 높은 준수율. v3.7.1 실측에서 5/5 Worker가 준수.
