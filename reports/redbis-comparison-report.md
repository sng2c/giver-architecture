# 통제 실험: 모놀리식 vs Giver v2.3 (측정 데이터)

> 동일 과제, 동일 인력, 동일 환경에서 모놀리식과 Giver v2.3를 비교.
> 이전 실험(v2.2)과 달리 **모놀리식의 실측 토큰 데이터**가 있음.

## 실험 설계

| 항목 | 모놀리식 | Giver v2.3 |
|------|----------|-----------|
| 과제 | Redis 프록시 10개 모듈 구현 (113개 테스트) | 동일 |
| 결과 | ✅ 113/113 테스트 통과 | ✅ 113/113 테스트 통과 |
| 산출물 | 540줄 (10개 파일) | 498줄 (10개 파일) |
| 방식 | 단일 Worker 서브에이전트 (fork 상속) | 3개 체인 (Scout→Planner→Scout→Worker) |
| 컨텍스트 | FORK (부모 대화 전체 상속) | Fresh (각 에이전트 초기화) |
| 측정 | Worker 서브에이전트 아티팩트 | 서브에이전트 아티팩트 |

## 모놀리식 단일 Worker (실측)

## 분석

### Giver가 모놀리식보다 43% 더 비싼 이유

2번체인과 3번체인에서 Planner가 283K, 301K로 높음. 원인:

1. **Planner가 10개 파일의 테스트 코드를 모두 읽음** — Task Splitting 규칙("3+ 파일 태스크 분할")이 모듈 수준에서는 적용되지 않았음. 각 체인이 2-4개 모듈을 담당하더라도 전체 파일을 읽는 경향
2. **Worker도 과도한 파일 읽기** — 2번체인 Worker 369K로 높음. 스코프 내 파일만 읽지 않고 전체 프로젝트를 읽음

### 가장 효율적인 체인이 81% 절감

1번체인(160K)은 파일 수가 적고(4개) 스코프가 좁아 효율적. Planner 85K 🟡, Scout 19K 🟢, Worker 55K 🟢. 이것이 Giver의 이상적인 작동 패턴.

### v2.2 실험과의 비교

| 지표 | v2.2 실험 | v2.3 실험 |

| Task Splitting | 미적용 | 부분 적용 |

### 발견된 문제

1. **Planner 과도 읽기**: 2번/3번체인에서 Planner가 283K/301K. 테스트 파일 전체를 읽지 않아도 됨. Scout가 이미 타겟팅된 리컨을 제공했으므로 Planner는 plan.md 작성에만 집중해야 함.

2. **Worker 과도 읽기**: 2번체인 Worker 369K. 스코프 내 파일만 읽어야 함.

3. **Task Splitting 미적용**: 10개 파일 → 3체인(4+3+2)으로 분할했지만, 각 체인 내에서도 Planner와 Worker가 스코프 외 파일을 읽음.
