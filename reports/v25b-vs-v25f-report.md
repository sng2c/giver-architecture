# v2.5b vs v2.5f 비교분석

## 개요

| 지표 | v2.5b | v2.5f | 차이 |
|------|------:|------:|-----:|
| 총 입력 토큰 | 381K | 738K | +357K (+94%) |
| 체인 수 | 3 | 2 | -1 |
| Worker 최대 | 103K | 180K | +77K |
| Planner 최대 | 46K | 328K | +281K |
| 직접 파일 조작 | 0건 | 1건 | +1 |
| 테스트 결과 | 113/113 통과 | 113/113 통과 | 동일 |

v2.5f가 v2.5b보다 **94% 더 많은 토큰**을 사용. 결과는 동일(113/113 통과).

## 체인별 상세 비교

### Chain 1: S-P-S-W (동일한 6파일)

| 역할 | v2.5b 입력 | v2.5f 입력 | 차이 | v2.5f 예산 |
|------|----------:|----------:|-----:|----------:|
| Scout 1 | 63K | 23K | -40K | 50K |
| Planner | 46K | 17K | -29K | 50K |
| Scout 2 | 4.3K | 18K | +14K | 50K |
| Worker | 42K | 180K | +138K | 80K |
| **Total** | **155K** | **238K** | **+83K** | |

**v2.5b Worker 42K vs v2.5f Worker 180K = 4.3배 차이.**

v2.5b: Scout 1이 63K로 과세 (63K > 예산), 하지만 Worker에게 DI를 충분히 제공해서 Worker가 42K만으로 구현
v2.5f: Scout 1이 23K로 절약, Planner 17K로 절약, but Worker가 180K - **DI 불충분으로 Worker가 파일 직접 읽음**

이것이 핵심: **Scout에서 절약한 토큰이 Worker에서 4.3배로 돌아옴.**

Worker turns: v2.5b=7, v2.5f=12 (71% 더 많은 턴 = 더 많은 파일 읽기)
Worker tools: v2.5b=9, v2.5f=18 (2배 더 많은 도구 호출 = 탐색적 동작)

### Chain 2: P-S-W

| 역할 | v2.5b 입력 | v2.5f 입력 | 차이 | v2.5f 예산 |
|------|----------:|----------:|-----:|----------:|
| Scout | 5.6K | 78K | +73K | 50K |
| Planner | 45K | 328K | +282K | 50K |
| Worker | 103K | 94K | -9K | 80K |
| **Total** | **154K** | **500K** | **+346K** | |

**v2.5f Planner 328K = 예산 50K의 6.55배.**

이것은 v2.5f C2의 핵심 병목. 원인:
1. **파일 수**: v2.5b C2=1파일(handler) vs v2.5f C2=4파일(handler+connection+server+index)
2. **Planner 과독**: 21턴, 25 툴콜 = 제한 없이 파일 읽음
3. **Scout 과세**: 78K = 예산 50K 초과, 불필요한 탐색

v2.5b: handler 1파일만 처리 → Scout 5.6K, Planner 45K, Worker 103K
v2.5f: 4파일 처리 → Scout 78K, Planner 328K, Worker 94K

### Chain 3: P-W (v2.5b만)

| 역할 | v2.5b 입력 | v2.5f | 
|------|----------:|------:|
| Planner | 35K | - |
| Worker | 37K | - |
| **Total** | **73K** | - |

v2.5b C3: connection, server/index, index 3파일을 별도 체인으로 처리.
v2.5f는 이 3파일을 C2에 포함 → C2 과부하 원인.

## 근본 원인 분석

### 1. 분할 전략 차이

```
v2.5b: 6파일(C1) → 1파일(C2) → 3파일(C3) = 3체인
v2.5f: 6파일(C1) → 4파일(C2)           = 2체인
```

v2.5f Giver가 C2에 4파일을 넣은 것은 **의존성 레이어 기준**:
- C1: Layer 0-1 (기반 모듈, 다른 프로젝트 파일 의존 없음)
- C2: Layer 2+ (C1 산출물에 의존)

하지만 **4파일 = C2 Planner 328K**. v2.5b는 같은 Layer 2+를 2체인으로 쪼갬:
- C2: handler 1파일 (의존성 많지만 파일 1개)
- C3: connection + server + index 3파일

**의존성 깊이뿐 아니라 파일 수도 분할 기준이어야 한다.**

### 2. DI 품질 차이

v2.5b C1 Scout: 63K (과세하지만)
v2.5f C1 Scout: 23K (절약하지만)

v2.5b는 Scout가 충분히 많이 읽어서 DI 커버리지가 높았음.
v2.5f는 Scout가 적게 읽어서 DI에 누락이 있었고,
Worker가 누락된 인터페이스를 직접 파일에서 읽음 → 180K.

**Scout 절약 = Worker 폭발.** 균형이 중요.

### 3. Planner 읽기 통제

v2.5b Planner: 최대 46K (8턴, 14 툴콜)
v2.5f Planner: 최대 328K (21턴, 25 툴콜)

v2.5b Planner는 Target Files와 Scout 결과만 읽음.
v2.5f Planner는 제한 없이 파일 읽음 → 21턴 = 맥락 계속 누적.

**Planner의 읽기 턴 제한이 필요.** 8턴/14툴콜(v2.5b) vs 21턴/25툴콜(v2.5f).

### 4. Turn 분포 비교

v2.5b 총 턴: 6+8+3+7 + 4+8+12 + 8+7 = 63턴
v2.5f 총 턴: 4+3+4+12 + 21+7+8 = 63턴

총 턴은 동일! 하지만 분포가 다름:
- v2.5b: 각 역할에 턴이 균등 분배
- v2.5f: C2 Planner에 턴 집중 (21/63 = 33%)

## 결론

| 교훈 | v2.5b가 더 나은 이유 | v2.5f 개선 필요 |
|------|---------------------|-----------------|
| 분할 | 파일 수 기준으로 세분 (1-2파일/체인) | 4파일/1체인 → 과부하 |
| DI 품질 | Scout가 충분히 읽어 Worker 경량화 | Scout 절약 → Worker 4.3배 |
| Planner 통제 | Target Files만 읽음 (8턴) | 무제한 읽기 (21턴/328K) |
| 체인 수 | 3체인 = 73K/체인 평균 | 2체인 = 369K/체인 평균 |

v2.5b의 교훈: **Scout에 투자하고 Worker에서 절약. Planner 읽기 제한. 파일 수로 분할.**
