# Monolithic vs Giver v2.4 — 통제 실험 리포트

> 실험 일시: 2026-05-20
> 과제: Redis-like proxy 서버 10개 소스 모듈 구현 (113개 테스트 통과)
> 모델: glm-5.1:cloud (전 실험 동일)

## 1. 실험 설계

동일한 과제를 두 가지 방식으로 수행:

| 방식 | 설명 | 컨텍스트 |
|------|------|---------|
| **모놀리식** | 단일 Worker가 전체 대화 기록(FORK)을 물고 10개 파일 한 번에 구현 | FORK (부모 세션 전체 상속) |
| **Giver v2.4** | 3개 체인으로 분할 (4+3+2 파일), 각 체인: Planner→Scout→Worker | clean (독립 컨텍스트) |

### v2.4 SKILL 변경사항 (v2.3 대비)

| # | 규칙 | 문제 원인 | 해결 |
|---|------|----------|------|
| 1 | 연속 체인 자동 실행 | 다중 체인 시 사용자 확인 대기로 지연 | 계획된 체인은 연속 실행, 실패 시에만 사용자 결정 |
| 2 | 재시도 시 사용자 결정 | 자동 재시도가 fde94195 3.3M 누적 유발 | 실패 시 분류와 제안을 보고, 사용자가 재시도/수정/중지 결정 |
| 3 | Planner 과도 읽기 금지 (v2.3) | Planner가 Target Files 외 파일 읽기 (283K~300K) | "Read ONLY Target Files + Scout recon" 명시 |
| 4 | Previous Failures 요약 필수 (v2.3) | 이전 체인 전체 출력 복사 (3.3M) | 2-4줄 요약, 전체 출력 복사 금지 |
| 5 | Worker 파일 생성 강조 (v2.3) | Worker가 진행 보고서 작성 | "Write actual source files to disk" 명시 |


## 6. 핵심 발견

### ✅ 검증된 가설

1. **Planner 과읽기 해소**: v2.3의 283K/300K → v2.4의 46K/48K. "Read ONLY Target Files" 규칙이 실효.
2. **최적 체인은 모놀리식 대비 -84%**: 137K vs 857K. Giver 아키텍처의 효율성 입증.
3. **이상적 에이전트 비율 78%**: 7/9 에이전트가 80K 이하. v2.3의 4/9 (44%)에서 대폭 개선.
4. **Scout 역할 검증**: 13-31K로 정찰 수행. 가벼운 컨텍스트로 정확한 recon 제공.

### ⚠️ 잔여 이슈

1. **체인 3 Worker 208K**: 2개 파일에 208K 소모. 서버 파일이 다른 모듈 의존성을 많이 포함.
   - 원인: connection.ts/server.ts가 config, logger, command/handler, storage 등 거의 모든 모듈 import
   - 해결 방안: Worker brief에 import 의존성만 포함 (전체 코드 아님)
2. **체인 1 Worker 170K**: 첫 체인의 Worker가 아직 80K 한계 초과.
   - 원인: 4개 파일을 한 번에 구현 (가장 많은 파일 수)
3. **3체인 합산시 +25% 절감에 그침**: 개별 체인은 효율적이나 합산하면 모놀리식 대비 25% 절감만.
   - 실무에서는 병렬 실행이 가능하므로 시간 효율은 병렬 실행 시 단축
   - 토큰 합산은 중복 brief 오버헤드 (Planner 계획 + Scout 정찰 × 3회)

### 📊 규칙 준수율 추이

| 규칙 | v2.2 | v2.3 | v2.4 | 유형 |
|------|------|------|------|------|
| context: fresh | 100% | 100% | 100% | 자동 (JSON 템플릿) |
| Scout 3요소 템플릿 | 75% | 100% | 100% | 준자동 |
| Planner 과읽기 금지 | 25% | 33% | **100%** | 판단 (규칙 강화로 해소) |
| Worker 80K 이하 | 50% | 33% | **33%** | 판단 (미해결) |

> **핵심 통찰**: "판단이 필요한 규칙"은 준수율이 낮지만, **구조적 제약으로 전환하면 100% 달성 가능**.
> Planner 과읽기 금지는 v2.3에서 "판단" 규칙(33%)이었으나, v2.4에서 강화된 명령어로 100% 달성.
