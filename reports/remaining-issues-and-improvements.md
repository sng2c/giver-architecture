# 잔존 과제 개선 방안

v2.1 검증에서 식별된 4가지 잔존 과제와 구체적 개선 방안.

---

## 1. 태스크 분할 미적용 — 4.9M Worker (110턴) 발생

### 문제

v2 SKILL.md에 "3+ 파일 변경 시 반드시 분할" 규칙이 있음에도, 프론트엔드 전체 분해 작업에서 Worker 하나가 110턴, 4.9M 입력으로 실행됨. 분할이 트리거되지 않았음.

**실측 데이터:**

| Run | 에이전트 | 입력 | 턴 | 태스크 |
|-----|---------|------|-----|--------|
| b99a2bd1 | Worker | **4.9M** | **110** | 프론트엔드 전체 분해 |

**원인 분석:**

1. **Giver가 "3+ 파일"을 태스크 분할의 기준으로 사용하지만**, 프론트엔드 분해는 "파일 몇 개를 수정하는가"가 아니라 "몇 개의 독립 모듈로 추출하는가"가 기준이어야 함. PTTPlugin.kt 추출도 마찬가지 — 1개 파일에서 5개 모듈을 추출하는 것은 5개 파일 수정과 동등.

2. **SKILL.md의 분할 규칙이 파일 수만 기준.** 현재: "Changes touching 3 or more files MUST be split." 하지만 1개 파일에서 여러 모듈을 추출하는 리팩토링은 파일 수 기준을 우회함.

3. **Worker 자체가 분할을 요청하는 메커니즘이 없음.** Worker가 "이 태스크는 너무 큽니다"라고 Giver에게 에스컬레이션하는 경로가 없음.

### 개선 방안

**A. 턴 수 기준 추가 (SKILL.md 수정)**

파일 수뿐만 아니라 예상 복잡도도 분할 트리거에 포함:

```
| 기준 | 분할 전략 |
|------|----------|
| 1-2 파일, 10턴 이내 | 단일 Worker |
| 3+ 파일 OR 1파일에서 3+ 함수 추출 | 병렬/순차 분할 |
| 예상 30턴 이상 | 반드시 분할 |
```

**B. Worker 에스컬레이션 규칙 추가**

Worker가 태스크 수행 중 예상 턴 수를 크게 초과하거나 plan.md의 스코프를 벗어나는 것을 감지하면 `contact_supervisor`로 Giver에게 보고:

```
Worker가 다음을 감지하면 즉시 contact_supervisor:
- plan.md의 Tasks가 5개 이상이고 각각이 독립적인 파일 수정인 경우
- 예상 턴 수가 30턴을 초과할 것으로 판단되는 경우
- 현재 턴이 30턴을 초과한 경우
```

**C. Giver의 사전 평가 강화**

Giver가 Planner에게 브리핑하기 전, 태스크 복잡도를 평가:

```
태스크 복잡도 평가 (Giver Phase 1.5 전):
- 함수/메서드 추출 3개 이상 → 분할 필수
- 새 파일 생성 3개 이상 → 분할 필수
- 예상 코드 변경 라인 100줄 이상 → 분할 고려
- 기존 파일 1개에서 여러 독립 변경 → 분할 필수 (함수 단위)
```

## 2. Worker 이상적 비율 하락 (20% → 11%)

### 문제

v2에서 Worker 이상적(≤80K) 비율이 20%였으나, v2.1에서 11%로 하락.

**실측 데이터:**

| 등급 | v2 (5건) | v2.1 (9건) | 변화 |
|------|---------|-----------|------|
| 🟢 ≤80K | 1 (20%) | 1 (11%) | -9pp |
| 🟡 ≤200K | 0 (0%) | 1 (11%) | +11pp |
| 🟠 ≤500K | 1 (20%) | 3 (33%) | +13pp |
| 🔴 >500K | 3 (60%) | 4 (44%) | -16pp |

**원인 분석:**

v2.1에는 대형 리팩토링 태스크가 다수 포함:

| 태스크 유형 | 건수 | 대표 입력 |
|------------|------|----------|
| 버그 수정 | 3건 | 38K, 174K, 393K |
| 리팩토링(1파일 추출) | 4건 | 285K, 715K, 746K, 1.1M |
| 리팩토링(전체 분해) | 1건 | **4.9M** |
| 리팩토링(hook 추출) | 1건 | 385K |

버그 수정 Worker만 보면 38K/174K/393K로 이상적~수용 범위. 하락은 리팩토링 비중 증가(조별 편향)이지 아키텍처 회귀가 아님.

### 개선 방안

**A. 이상적 비율을 태스크 유형별로 분리하여 보고**

분석 리포트에서 Worker를 태스크 유형별로 분리:

```
Worker 이상적 비율:
- 버그 수정: 1/3 (33%) → v2와 동급
- 리팩토링: 0/6 (0%) → 태스크 분할 필요 (과제 1 해결 시 개선)
- 전체: 1/9 (11%)
```

**B. 과제 1(태스크 분할)이 해결되면 리팩토링 Worker도 이상적 범위 진입 예상**

함수 단위 분할(Worker당 3-5개 함수)이 적용되면:

| 태스크 | 현재 | 분할 후 예상 |
|--------|------|------------|
| PTTPlugin 5개 추출 | 4.0M (1 Worker) | ~200K × 5 Workers |
| 프론트엔드 분해 | 4.9M (1 Worker) | ~200K × 4 Workers |
| PTTPlugin thin delegate | 715K + 285K | ~170K × 3 Workers |

**C. Worker 타겟 헤더를 SKILL.md에 명시**

```
Worker 이상적 입력:
- 버그 수정: ≤80K
- 함수 추출 (1-2개): ≤200K  
- 모듈 분해 (3+파일): ≤200K (분할 필수)
- 전체 리팩토링: 분할 없이는 불가능 → 반드시 분할
```

## 3. Scout 평균 소폭 증가 (105K → 133K)

### 문제

v2에서 105K였던 Scout 평균이 v2.1에서 133K로 27% 증가.

**실측 데이터:**

| 등급 | v2 (5건) | v2.1 (13건) | 변화 |
|------|---------|-----------|------|
| 🟢 ≤80K | 2 (40%) | 5 (38%) | -2pp |
| 🟡 ≤200K | 3 (60%) | 5 (38%) | -22pp |
| 🟠 ≤500K | 0 (0%) | 3 (23%) | +23pp |

v2.1에 280K, 369K, 238K 등 대형 리컨이 포함되어 평균이 상승.

**원인 분석:**

| 대형 Scout | 입력 | 태스크 |
|-----------|------|--------|
| fd8c9e26 | 280K | PTT 오디오 GAP 5개 항목 리컨 |
| 58463578 | 369K | 오디오 GAP 구현 리컨 |
| 786c8297 | 238K | PTTPlugin 남은 추출 가능 코드 리컨 |

3건 전부 "广범위 리컨" — 타겟팅 지시가 있었으나 태스크 자체가 여러 항목을 포함.

### 개선 방안

**A. Scout output limit을 200줄에서 150줄로 강화**

현재 SKILL.md: `"Keep output under 200 lines"`
개선: `"Keep output under 150 lines. Include ONLY function signatures and relevant code sections — never include full file contents."`

200줄도 충분히 타겟팅되지만, 5개 항목 리컨에서는 200줄 내에 정확한 타겟을 잡기 어려움. 150줄로 줄이면 핵심만 발췌하도록 압박.

**B. 복합 리컨의 분할 지시**

여러 항목을 리컨해야 할 때 Scout 1회가 아닌 항목별로 Scout를 나누어 호출:

```
Bad:  "Recon 5 audio GAP items in PTTPlugin.kt"
Good: Giver가 5개 항목을 식별한 후:
      - Scout 1: "Recon GAP #1 and #2 only"
      - Scout 2: "Recon GAP #3 and #4 only"
      - Planner 브리핑에 5개 항목 요약 포함
```

**C. Giver의 사전 스코프 분할**

Phase 0.5에서 Giver가 리컨 범위를 평가:

```
리컨 범위가 3개 이상의 독립 항목이면:
→ Scout를 항목별로 분할하거나
→ Planner 브리핑에 "Scout 리컨이 포괄적이지 않을 수 있음. plan.md에서 필요 시 추가 리컨" 명시
```

## 4. v2-era Fork 위반 1건

### 문제

v2 SKILL이 이미 커밋된 동일 세션에서 fork 호출 3건이 발견됨.

**실측 데이터:**

| Run | 에이전트 | 입력 | 컨텍스트 | 시각 |
|-----|---------|------|---------|------|
| 12a6626e | planner | 447K | **FORK** | 05-19 13:50 |
| 12a6626e | scout | 458K | **FORK** | 05-19 13:51 |
| 12a6626e | worker | 1.7M | **FORK** | 05-19 13:55 |

**원인 분석:**

v2 SKILL이 05-19 19:15 KST에 커밋되었으나, 이 세션은 05-19 19:18 KST에 시작됨. fork 위반은 13:50 UTC (= 22:50 KST 전날)에 발생. 즉, v2 SKILL이 아니라 **v1 SKILL이 적용된 세션**에서의 위반.

이전 v2 분석에서 이 세션을 누락한 이유: 동일 run_id(12a6626e)의 서브에이전트 3건이 v2 분석 시간대 경계 밖에 있었으나, v1 분석에서도 포함되지 않았음.

### 개선 방안

**A. 세션 경계 감지 로직 추가**

pi-analyze에 세션 시작 시각 기준으로 v1/v2/v2.1 분할:

```python
# v1: 세션 시작 < v2 SKILL 커밋 시각
# v2: v2 SKILL 커밋 ≤ 세션 시작 < v2.1 SKILL 커밋
# v2.1: v2.1 SKILL 커밋 ≤ 세션 시작
```

**B. SKILL.md를 읽은 세션만 v2+로 분류**

세션 로그에서 SKILL.md를 읽은 기록이 있는 세션만 v2+로 간주. SKILL.md를 읽지 않은 세션은 v0/v1 처리.

**C. 실제 영향은 미미**

이 fork 위반은 v1 era에서 발생한 것으로, v2/v2.1 데이터에 포함되지 않음. 분석 경계를 명확히 하면 됨.

## 부록: 규칙 준수율 분석 — "해라" vs "하지 마라" vs "자동 반복"

초기 분석에서 "하지 마라 금지 규칙이 비용 0이라 준수율이 높다"고 결론내렸으나, 이는 틀렸다.

### 정정: pi-subagents 기본값은 fork

pi-subagents의 `context` 기본값은 **fork** (부모 컨텍스트 상속)이다. 따라서:

| v1 호출 | 비율 | 실제 동작 |
|---------|------|----------|
| empty/default | 90% | **기본값 fork = 부모 컨텍스트 상속** |
| 명시적 fork | 6% | 기본값과 동일 |
| 명시적 fresh | 3% | 유일하게 격리된 호출 |

v1의 90% empty는 "아무것도 안 한 것"이 아니라 **기본값(fork)을 그대로 사용한 것**이다. fork 금지 + fresh 명시는 "하지 않는 것"이 아니라 **매 호출마다 기본값을 명시적으로 오버라이드하는 적극적 행동**이다.

### 준수율의 진짜 구분: 자동 반복 vs 판단 필요

| 성질 | 규칙 | 준수율 | 왜? |
|------|------|--------|-----|
| **JSON에 내장 (자동 반복)** | `context:"fresh"` 명시 | 100% | SKILL.md의 호출 템플릿에 포함 → 매 호출마다 자동 삽입 |
| **JSON에 내장 (자동 반복)** | fork 금지 | 100% | 동일. 템플릿에 포함되면 자동 |
| **JSON에 내장 (자동 반복)** | Scout 선행 | 100% | 체인 템플릿에 포함 → 자동 |
| **판단 필요** | 태스크 분할 (3+ 파일) | **0%** | Giver가 상황 판단 필요. 템플릿에 넣을 수 없음 |
| **판단 필요** | 브랜치 per chain | **~4%** | git 명령 실행 필요. Giver가 능동적으로 실행해야 함 |
| **자연스러운 대화** | 협업 진단 (Phase 0.5) | **75%** | 사용자와의 대화 흐름 안에 있음. 자연스러운 턴 |
| **판단 필요** | Scout 타겟팅 | **40%** | Giver가 타겟팅 지시를 작성해야 함 |

### 핵심 통찰

준수율을 결정하는 것은 **"해라 vs 하지 마라"가 아니라 "자동 반복 vs 판단 필요"**이다:

1. **자동 반복 (준수율 100%):** SKILL.md의 JSON 템플릿이나 체인 구조에 내장되면, Giver가 매번 복사-붙여넣기하므로 100% 준수. `context:"fresh"`가 대표적.

2. **판단 필요 (준수율 0~4%):** Giver가 상황을 판단하여 능동적으로 실행해야 하는 규칙. 태스크 분할, 브랜치 생성. 판단을 생략하면 규칙이 무시됨.

3. **자연스러운 대화 (준수율 75%):** 사용자와의 대화 흐름 안에 자연스럽게 포함되는 규칙. 협업 진단. Giver가 질문하고 사용자가 응답하는 패턴.

### 개선함에 대한 시사점

루� 추가보다 **자동 반복 구조로 만드는 것**이 효과적이다:

- `context:"fresh"` → JSON 템플릿에 포함 → **100%** (판단 불필요)
- Scout 타겟팅 → 템플릿에 "what/where/output limit" 포함 → **40%** (판단 필요하지만 템플릿이 가이드)
- 태스크 분할 → 템플릿만으로 불가 → **0%** (상황 판단 필요)
- 협업 진단 → 대화 흐름에 포함 → **75%** (자연스러운 패턴)

태스크 분할 0%를 해결하려면 "3+ 파일 시 분할" 규칙 추가보다, **Giver가 판단하기 쉬운 구조적 트리거**가 필요하다. 예: 체인 구성 시 Worker에게 파일 목록을 전달하기 전에 Giver가 파일 수를 카운트하는 단계를 Phase에 명시적으로 포함.
